# AI Usage Disclosure

In the spirit of complete transparency for the Digital Alpha Technologies assignment, this document outlines exactly how and where Artificial Intelligence was utilized during the development of this codebase.

### AI Tools Used
- **Agentic AI Assistant**: Acted as a pair-programming partner executing direct terminal commands, writing code via direct file edits, running linters, and scaffolding the architecture based on my strict prompts.

### Where AI Was Used
The AI was heavily utilized to accelerate boilerplate generation and repetitive typing. Specifically, it was used to:
1. Scaffold the Next.js and FastAPI monorepo directory structure.
2. Generate the repetitive Pydantic schemas (e.g., typing out `min_amount: Optional[float] = None` repeatedly).
3. Generate the Tailwind CSS class strings for the layout based on my visual design instructions (e.g., asking it to apply "glassmorphism and strict dark mode aesthetics").
4. Translate my mathematical instructions into SQLAlchemy aggregation queries for the Recharts endpoints (grouping by category).

### Examples of AI-Generated Work
- **The Seed Script (`backend/scripts/seed.py`)**: The AI wrote the bulk of the JSON parsing loop that reads the `transactions.json` file, normalizes the timestamps, and batches the inserts into PostgreSQL.
- **The UI Components (`src/components/ui/*`)**: The base functional shells for buttons, modals, and the drawer were generated by the AI, and then subsequently modified by me to fit the exact design needs.

### Examples of AI Output Rejected/Fixed

While the AI was a powerful typing accelerator, it fundamentally lacked the architectural foresight required for the strict constraints of this assignment. I had to manually reject and fix its output in several critical areas:

1. **Rejection 1: The Transaction Table Architecture**
   - **What the AI proposed**: When I asked the AI to build the table, it immediately tried to `npm install @tanstack/react-table` because its training weights heavily associate modern React tables with TanStack.
   - **Why I rejected it**: The assignment explicitly prohibited the use of third-party data-grid libraries.
   - **How it was fixed**: I rejected the AI's proposal, forced it to uninstall the library, and explicitly instructed it to build a raw HTML table (`<table>`, `<thead>`, `<tbody>`) and manage the pagination state manually via TanStack Query parameters.

2. **Rejection 2: The Rewards Redemption Race Condition**
   - **What the AI proposed**: When implementing the `/api/rewards/{reward_id}/redeem` endpoint, the AI wrote standard CRUD logic: it queried the user, checked `if balance >= cost`, subtracted the balance, and called `db.commit()`.
   - **Why I rejected it**: This approach is vulnerable to race conditions (Time-Of-Check to Time-Of-Use bugs). If two requests arrive at the exact same millisecond, they both read the old balance, allowing a user to double-spend their coins. 
   - **How it was fixed**: I rejected the naive implementation and instructed the AI to rewrite the endpoint utilizing PostgreSQL row-level locking. I forced it to use SQLAlchemy's `.with_for_update()` on the User query, ensuring absolute database atomicity.

3. **Rejection 3: Client-Side Math for Balance Updates**
   - **What the AI proposed**: After a successful reward redemption, the AI updated the React state by simply doing `setBalance(prev => prev - cost)` in the frontend.
   - **Why I rejected it**: The assignment requirements mandate that the backend remains the absolute source of truth. Client-side math can drift out of sync if another browser tab or mobile device redeems a reward simultaneously.
   - **How it was fixed**: I removed the client-side state manipulation and replaced it with `queryClient.invalidateQueries({ queryKey: ["balance"] })`, forcing the frontend to safely refetch the authoritative balance from PostgreSQL.
